# AGENTS.md

## 1. Название проекта и цель
**SMT Local Bot (analiz-slivov)** — локальный Telegram‑бот и ETL/streaming‑pipeline для работы с телематическими данными (Wialon, SMT и др.). Цель: развязать бизнес‑логику от Wialon‑legacy, хранить снапшоты/метаданные локально, обеспечивать быстрый поиск, карточки объектов, отчёты и сервисные функции.

- `bot/` — пакет с инфраструктурой бота (логирование, token store, WialonClient) и фиче‑модулями. Уже выделены `bot/features/reports.py`, `bot/features/search.py`, остальные блоки постепенно выносятся сюда.
- `bot_new.py` — бот: команды, карточки, настройки, локальный поиск, интеграция с pipeline/Wialon (по мере миграции становится тонким glue).
- `pipeline/services/unit_snapshot_service.py` — единый снапшот (`data/unit_snapshot.json.gz`).
- `pipeline/cli/run_stream.py` (+ `.ps1`) — запуск стриминга/ingestion.
- `pipeline/config/unit_config.py` — датаклассы UnitConfig (общие поля, HW, сенсоры, калибровки XY и X a b, валидация).
- `pipeline/adapters/wialon_wlp_import.py`, `pipeline/cli/import_wlp.py` — импорт `.wlp` в UnitConfig/локальное хранилище, дальнейшая работа бота из собственных конфигов.
- `docs/wialon_unit_structure.md`, `docs/unit_config_schema.md` — документация/схемы.
- `logs/unit_snapshot_watch.log` — журнал ребилдов снапшота и метаданных устройства (каталог `logs/` не коммитим).
- `scratch/` — локальное хранилище артефактов/дампов (`account_*.html`, `tmp_*`, выгрузки). Всё, что не должно попадать в git, складываем сюда (игнорируется правилом `.gitignore`).
- `tests/` — тесты pipeline/снапшота/метрик.

## 4. Правила кода и ключевые зависимости
- Стиль: PEP8 + type hints, логирование через `logging`.
- Снапшот формируется только через `UnitSnapshotService`; `data/units.v1.json.gz` удалён.
- UnitConfig наполняется из `.wlp` (или других источников) собственным импортёром; бот/поиск работают исключительно на локальных данных.
- Перед крупными правками `bot_new.py` — делаем бэкап `bot_new.py.bak.YYYYMMDDHHMMSS`.
- Env vars: `PIPELINE_WIALON_TOKEN`, `PIPELINE_WIALON_EXTRA_TOKENS`, `PIPELINE_SOURCE_KIND`, `UNIT_DEVICE_*`, `PYTHONPATH`.

## 6. Статус и курс
- Сделано:
  - Карточка полностью работает от локального `UnitConfig`/`pipeline` (поиск, параметры, блок «🧷 Датчики»).
  - Инструменты импорта (`import_wlp`, `UnitConfigService`) прокачаны для сенсоров/калибровок; добавлена команда «➕ Добавить ДУТ» с копированием датчиков из Wialon в локальный конфиг.
  - Появились кнопки «🔧 Настройки датчиков» и «📈 Тарировка ДУТ»: просмотр локальных значений/таблиц, логирование действий, CSV‑экспорт.

- Карточка показывает локальные значения ДУТ1/ДУТ2/ДУТа, обрабатывает «сырой диапазон» (0 или >4096) и подставляет источники (`adc11`, `[ДУТ1]+[ДУТ2]`).
- Веб-интерфейс «Мониторинг» полностью удалён; система работает только через Telegram-бота и локальный pipeline.
- 2025‑11‑14: из бота и репозитория полностью удалены «📊 Анализ сливов», связанные графики, message-cache и вспомогательные скрипты `drain_*`. Переписывать будем отдельно после стабилизации pipeline.
- В работе:
  - Автоматические обновления тарировки напрямую из СМТ (сейчас API `core/search_item` для некоторых датчиков не возвращает `tbl`; нужно эскалировать в поддержку и/или найти дополнительный флаг/метод).
  - Документирование (`docs/unit_config_schema.md`), тесты UnitConfig/pipeline, расширение адаптеров для других СМТ, редактор overrides в боте.
  - Новый дизайн анализа сливов: нужно продумать API/интеграцию поверх `detector.py`, прежде чем возвращать кнопку в UI.
- Далее:
  - Доработать ingestion для стабильного покрытия всех юнитов (включая новые ID), чтобы карточка всегда находила события.
  - После решения вопроса с API — автоматизировать синхронизацию `tbl` при добавлении/обновлении сенсоров.

## 7. Прогресс текущей сессии (2025‑11‑13)
### Сделано
- Перевели запросы тарировки на официальный `core/search_item` (`flags=4097`), отказались от неофициального `unit/get_sensors`.
- Реализовали обход ссылок: если у кастомного ДУТа нет `tbl`, ищем её у датчиков/параметров, на которые он ссылается (например, `rs485_fls12`).
- Добавлена кнопка «📈 Тарировка ДУТ» с локальным просмотром + inline‑кнопкой «🔄 Обновить из СМТ», логирование (`dut_cal_local`, `dut_cal_refresh`).
- Карточка теперь берёт строку «ДУТ (уровень топлива)» из основного ДУТа, а не из подчинённых, плюс показывает источники в скобках.
- Для произвольных датчиков включена проверка диапазона (0 или >4096 → «не работает (значение)»).
- Отладили отсутствие локальных данных: выяснили, что при отсутствии событий в `pipeline_storage` карточка падает в `no_event` и показали, как добивать ingestion.
### Необходимо
- Решить вопрос с отсутствием `tbl` в ответах `core/search_item` для ряда датчиков (`ДУТ1`, `ДУТ2`). Сейчас лог фиксирует `dut_cal_refresh: no calibration rows…`; без этого автоматическое обновление невозможное. Требуется поддержка Wialon/дополнительные флаги (см. документацию: [core/search_items](https://help.wialon.com/en/api/user-guide/api-reference/core/search_items), [Units → Sensors flags](https://help.wialon.com/en/api/user-guide/data-format/units), [Sensors: Calculation table explained](https://help.wialon.com/en/wialon-hosting/expert-articles/unit/sensors-calculation-table-explained)).
- Завершить документацию `docs/unit_config_schema.md` и добавить тесты для нового поведения сенсоров/тарировок.
- Расширить ingestion (run_stream) для гарантированной подкачки всех юнитов (в том числе `19688`/`2993уо…`), чтобы карточка всегда находила локальные события.
- Добавлен единый запуск `pipeline/cli/run_all.py`: поднимает бота, стрим и регулярное обновление снапшота по одной команде.

```

Шаги (строго по порядку):
1) Включи отдельный лог: logs/<feature>.log. Логируй этапы: входные данные; внешний вызов (метод/флаги/время/кол-во); ветвления с причинами; небольшой семпл ответа; ошибки по элементам с текстом исключения; итоговые счётчики; явный маркер успеха (saved/ok).
2) Напиши минимальный диагностический скрипт, который вызывает ровно тот же код/флаги, что и UI/кнопка. Выведи форму данных и 3 примера.
3) Сопоставляй цель по сильному ключу: id → имя → эвристика (параметр и т.п.). Всегда логируй, какой путь сработал.

5) Сразу проверь импорты/типы, задействованные в конвертации/сохранении. NameError/ImportError устраняй первым делом. Запусти python3 -m py_compile … до старта.
6) Вноси минимальный фикс (helper/адаптер), добавляй защиту от None/NaN/Inf и явные логи причин пропуска.
7) Перезапусти долгоживущий процесс. Убедись по логу, что пройдены все этапы и есть маркер успеха.
8) Сдай результат: минимальный diff; хвост целевого лога; одна строка «корень причины → фикс»; точные команды воспроизведения.

Быстрый чек‑лист (10 минут):
- Логи: есть отдельный файл? Метки этапов и причины ошибок логируются?
- Воспроизведение: скрипт дергает тот же код/флаги, что UI.
- Идентификация: id → имя → параметр (или иная эвристика).
- Форма данных: учтены x,y vs x,a,b; синонимы n/name, p/param/src; строки ↔ числа.

Правила инструментирования:
- Одна фича — один лог (logs/<feature>.log): start | api_fetch | matched_by=id/name/param | transform | item_error err=… | points_parsed=… | saved=… | done.
- Логируй только семпл (первые 3 элемента), без «простыней».
- Всегда логируй причину ветвления/пропуска.

Итоговая дисциплина:
«лог → локальный скрипт → форма данных → id/name/param → импорты → компиляция → перезапуск → хвост лога».
```
