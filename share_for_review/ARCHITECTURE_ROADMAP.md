# SMT Local Bot — архитектура доступа, иерархии и ingestion

Этот файл собирает в одном месте договорённости по тому, **как мы хотим развивать систему**: от первой задачи (ingestion Galileosky) до иерархии пользователей, групп ТС и работы с сырыми данными.

Файл не про мелкие детали UI, а про **каркас и последовательность работ**.

---

## 0. Цели и текущая база

У нас уже есть:

- локальное хранилище:
  - снапшот юнитов `data/unit_snapshot.json.gz` (`UnitSnapshotService`);
  - история сырой телеметрии `data/pipeline_storage/YYYY-MM-DD/events.jsonl` (`RawStorage`);
  - «срез» последних показаний `latest_metrics.json` (`LatestTelemetryStore`);
  - `UnitConfig` + сервис чтения/записи.
- ingestion из Wialon: `pipeline/cli/run_stream.py` + `pipeline/adapters/wialon/stream.py` + `pipeline/sources/wialon.py`.
- Monitoring v2 (FastAPI + JS фронт): список ТС, карта, карточка.

Наша цель — **сделать “мини‑Wialon” под одну компанию**, но с:

- прямым приёмом телеметрии (Galileosky и дальше другие терминалы),
- иерархией подразделений и пользователей,
- гибкими группами ТС,
- безопасным удалением и удобной работой с сырыми данными.

## 1. Приоритетный план (по этапам)

### Этап 1. Ingestion из Galileosky (высший приоритет)

1. Уточнить фактический протокол Galileosky:
   - какой режим используется сейчас (TCP, UDP, HTTP, «ретранслятор» и т.д.);
   - какая структура пакета / JSON, какие поля доступны (время, lat/lon, скорость, параметры).
2. Спроектировать «источник» под Galileosky:
   - добавить новый `source_kind="galileosky"` в `PipelineConfig`;
   - реализовать `GalileoskySourceProvider` по аналогии с `WialonSourceProvider`;
   - реализовать адаптер `pipeline/adapters/galileosky/stream.py`, который:
     - слушает нужный протокол (TCP/HTTP‑endpoint),
     - нормализует сообщения к `Event`,
     - вызывает `PipelineStorageService.store_events`.
3. В `run_stream.py`:
   - научиться выбирать провайдера по `PIPELINE_SOURCE_KIND=galileosky`;
   - дать минимальные параметры CLI/ENV для Galileosky (порт, формат, ключи).
4. Проверка:
   - поднять ingestion, направить 1–2 терминала Galileosky на наш сервер;
   - убедиться, что:
     - события появляются в `data/pipeline_storage/.../events.jsonl`;
     - `latest_metrics.json` обновляется;
     - Monitoring v2 показывает актуальное положение без Wialon.

Пока этот этап не закрыт, **все остальные доработки считаются вторичными**.

### Этап 2. Иерархия подразделений и владельцы объектов

1. Ввести сущность **узла структуры** (подразделения):
   - таблица/JSON `nodes` с полями:
     - `id`;
     - `parent_id` (null для корня);
     - `name` (любое: «Компания», «Управление 1», «Колонна 3», «Смена А»);
     - `order` (для сортировки).
2. Привязать ТС к узлам:
   - у `Unit` (в локальной модели) добавить `owner_node_id`;
   - при создании ТС в админке — выбирать узел (по умолчанию текущий в дереве);
   - при необходимости — давать админам возможность менять `owner_node_id`.
3. Правило видимости по структуре:
   - пользователь видит ТС, если `unit.owner_node_id` находится **в поддереве его узла**;
   - верхние уровни видят всё, что ниже; нижние не видят вверх.
4. В Monitoring API (`/web/api/units`, `/web/api/units/{id}`, `/web/api/units/feed`):
   - добавить зависимость от текущего пользователя;
   - перед выдачей фильтровать список ТС по доступным `node_id`.

### Этап 3. Пользователи и права

1. Ввести сущность `User`:
   - `id`, `login`, `password_hash`, `display_name`;
   - `node_id` — к какому узлу структуры привязан;
   - `manager_id` (опционально) — «старший» пользователь;
   - флаги прав:
     - `is_admin` (видит всё, может заходить в админку),
     - `can_manage_users`,
     - `can_manage_units` и т.п.
2. Авторизация:
   - WEB Monitoring авторизуется только через логин/пароль (`POST /web/api/login`);
   - сессия (`session_id`) всегда привязана к `user_id` и `node_id` и хранится в файловых сессиях (`data/web_v2_sessions`).
3. Проверка прав на сервере:
   - все `/web/api/admin/*` ручки доступны только при `is_admin` или соответствующих флагах;
   - Monitoring API использует `node_id` и (позже) группы для фильтрации.

### Этап 4. Группы ТС и дополнительная видимость

1. Ввести группы:
   - `Group`: `id`, `name`, `description`;
   - `UnitGroup`: связь many‑to‑many `unit_id` ↔ `group_id`.
2. Дополнительные права на группы:
   - у `User` добавить `allowed_group_ids` (список/связь many‑to‑many).
3. Правило видимости с учётом групп:
   - пользователь видит ТС, если:
     - `unit.owner_node_id` в его поддереве **ИЛИ**
     - `unit` состоит хотя бы в одной группе из `allowed_group_ids`.
4. Вкладка «Избранное»:
   - реализовать как специальную группу `favorites` на пользователя (user‑scoped):
     - при клике по ⭐ у ТС — добавлять/удалять связь с `favorites` выбранного пользователя;
     - вкладка `Избранное` в Monitoring просто фильтрует по этой группе.

### Этап 5. Админ‑UI внутри основной WEB‑системы

1. Добавить раздел «Админка» в существующий фронт:
   - доступен только пользователям с `is_admin`.
2. Вкладка «Структура»:
   - слева дерево узлов (drag‑and‑drop при необходимости);
   - справа:
     - список ТС узла (с возможностью сменить узел/удалить/архивировать);
     - список пользователей этого узла.
   - из этого экрана:
     - создавать/переименовывать/перемещать узлы;
     - создавать пользователей в выбранном узле.
3. Вкладка «Группы ТС»:
   - список групп;
   - для выбранной группы — двойной список: «все ТС» ↔ «ТС в группе»;
   - массовое добавление/удаление.
4. Вкладка «Пользователи»:
   - таблица всех пользователей (логин, имя, узел, старший, группы, флаги прав);
   - форма создания/редактирования:
     - выбор узла через дерево;
     - выбор старшего из пользователей этого узла;
     - выбор доступных групп.

### Этап 6. Управление объектами (создание, перенос, удаление)

1. Создание ТС:
   - инициируется в контексте узла (в «Структуре» или отдельной форме);
   - поле «Подразделение»:
     - по умолчанию текущий узел;
     - изменяемо только для пользователей с правами (например, `can_manage_units`).
2. Перенос ТС:
   - доступен админам/старшим: выбор другого узла — ТС переезжает вместе с видимостью.
3. Мягкое удаление (архив):
   - у ТС флаги:
     - `is_deleted`, `deleted_at`, `deleted_by`, `delete_reason`;
   - обычные пользователи видят только `is_deleted = false`;
   - в админке — отдельный фильтр/вкладка «Архив», откуда можно восстановить.

### Этап 7. Работа с сырыми данными (сообщения терминала)

1. API для событий:
   - `GET /web/api/units/{unit_id}/events?from_ts=&to_ts=&cursor=&limit=500`:
     - вычисляет соответствующие дни;
     - читает `events.jsonl` через `PipelineStorageService.fetch_day`;
     - фильтрует по `device_ts` и сортирует;
     - возвращает часть событий и `cursor` для догрузки.
2. UI «Сообщения» в карточке:
   - вкладка «Сообщения» у юнита:
     - выбор диапазона (Сегодня/24ч/7 дней/произвольно);
     - таблица: `№`, `Время`, `Коорд.`, `Скорость`, 1–2 ключевых параметра;
     - раскрытие строки → полный `params`/`raw_payload`;
     - бесконечный скролл (подгрузка по `cursor`).
   - подсветка:
     - разрывов связи (нет сообщений > N минут);
     - аномалий (резкий скачок топлива/скорости).
3. Экспорт:
   - опционально `GET /events?format=csv` для выгрузки периода в CSV.

### Этап 8. Улучшения UX Monitoring v2

1. Карточка объекта:
   - иконка в списке для явного открытия/закрытия карточки;
   - карточка одна, «прыгает» к выбранной строке, но не скрывается при выборе другого ТС — просто меняет содержимое;
   - разделение блоков параметров на 1–2 столбца адаптивно от ширины панели.
   - быстрый первый кадр из превью `/api/units` (card_preview), детали догружаются фоном; кеш деталей LRU 300 + TTL 60 с.
   - feed принимает `watch_ids` (видимые/выбранные/worklist) и отдаёт только нужные обновления — масштабируется на 20k+ объектов.
   - параметры/сенсоры лимитированы (params≤30, sensors≤8), служебные `raw_hex/unknown_*` скрыты из UI.
   - статусы: 🚗 движение, 🛑 остановка (короткая), 🅿️ стоянка (длительная); быстрые фильтры под эти статусы.
   - поиск: токены через пробел по имени/UID/рег.номеру/hw/адресу, опционально по ID (переключатель в поле поиска).
   - быстрый поиск по ID можно включать/выключать встроенным переключателем в поле поиска; фронт фильтрует только по выбранным полям (ID не ищется, если переключатель выключен).
2. Список:
   - вкладка `Избранное` (см. группы);
   - аккуратное поведение при ресайзе (уже частично реализовано: фиксирование высоты строки, обрезка meta‑текста и т.п.).
3. Отображение статусов:
   - более понятные текстовые метки: «Онлайн, в движении», «Онлайн, стоянка», «Нет связи 1.5 ч».

## 2. Резюме по приоритетам

Если коротко, в каком порядке имеет смысл двигаться:

1. **Galileosky/Wialon IPS ingestion** — новые прямые источники данных, чтобы уйти от зависимости только от Wialon Remote API.
2. **Иерархия + пользователи** — база доступа и видимости для диспетчеров/помощников.
3. **Группы ТС + Избранное** — удобная логическая группировка и быстрый доступ к ключевым объектам.
4. **Админ‑UI в основной WEB‑системе** — чтобы всё этим можно было управлять без правки файлов/конфигов.
5. **Мягкое удаление и перенос ТС** — безопасная эксплуатация при изменениях парка.
6. **UI для сырых данных** — удобная диагностика по сообщениям за период.
7. **Доработки UX Monitoring v2** — полировка интерфейса и качества жизни операторов.

Этот план не мешает делать мелкие багфиксы и косметические улучшения по пути, но **большие усилия** стоит вкладывать в этапы по порядку сверху вниз.

Состояние на 2025‑11‑22:

- Этап 1 (Galileosky/Wialon IPS ingestion) в рабочем состоянии: события стабильно попадают в `events.jsonl` и `latest_metrics`, контракт `Event/latest_metrics` формализован в `docs/events_schema.md`, для обоих источников есть health/metrics.
- Дальнейший фокус — этапы 2–4: иерархия/права, группы/Избранное, админ‑панель и UI для сырых данных поверх уже стабильного ingestion.

#### 1.1. Диагностика задержек телеметрии

- Важно различать:
  - задержку на уровне **сети/ретранслятора** (когда Wialon IPS отдаёт историю с запаздыванием);
  - и работу локального ingest’а (адаптеры, `LatestTelemetryStore`, Monitoring).
- Все адаптеры (`wialon_ips`, `galileosky`) принимают события «как есть» и сразу пишут `Event` в:
  - `data/pipeline_storage/YYYY-MM-DD/events-*.jsonl`,
  - `data/pipeline_storage/latest_metrics.json` (через `update_from_events`), без квантования «раз в N минут».
- Порог свежести в Monitoring всегда считается по `device_ts` (время в пакете) → если ретранслятор присылает пачку точек с `device_ts`, которые уже отстают от текущего времени на 20–40 минут, UI честно показывает «Нет данных N мин/ч» для всех этих событий.
- Практический чек‑лист:
  - на удалённом сервере: `tcpdump` по порту IPS и сравнение `DDMMYY;HHMMSS` из `#D#` с `date -u`;
  - на локальной машине: по конкретному `unit_id` посмотреть последовательность `device_ts/received_ts` в `events-*.jsonl` и возраст `device_ts` в `latest_metrics.json`;
  - если IPS‑пакеты на VPS свежие (разница секунд/пара минут), а в `latest_metrics.json` большинство `device_ts` старше 20–40 минут, значит источник/ретранслятор отдаёт историю; если и там времена свежие, искать проблему нужно уже в локальном ingest/времени системы.

## 3. UI‑детализация по ключевым зонам

Этот раздел фиксирует **то, как именно мы хотим видеть UI**, чтобы при реализации не вспоминать переписку.

### 3.1. Monitoring v2 (рабочий экран диспетчера)

Основная страница Monitoring остаётся такой же по структуре (список слева, карта справа), но с уточнениями:

- **Список объектов слева**
  - каждая строка:
    - слева иконка (например, `🛈` или маленькая карточка): клик по иконке **переключает карточку** этого объекта (открыть/закрыть);
    - текст клика по остальной части строки по‑прежнему выбирает объект и центрирует карту;
    - в правой части — скорость, статус, звезда `⭐` (избранное).
  - строка всегда фиксированной высоты (как сейчас), текст meta обрезается с `ellipsis`, чтобы не «ломать» соседние строки при сужении панели.

- **Карточка объекта**
  - существует **одна карточка на страницу**, которая «встраивается» в список под выбранной строкой:
    - клик по иконке/строке другого ТС → карточка переезжает под него и перерисовывается;
    - повторный клик по иконке того же ТС → карточка скрывается;
    - крестик `✕` внутри карточки тоже закрывает её.
  - карточка НЕ исчезает автоматически при выборе другого ТС — содержимое просто меняется (чтобы не было ощущения «мигания»).
  - блоки датчиков/сырых параметров:
    - при широкой панели — 2 столбца (уменьшаем высоту карточки, меньше прокрутки);
    - при узкой панели (ползунок близко к карте) — падаем обратно в 1 столбец, чтобы текст не «ломался».

- **Вкладки и «Избранное»**
  - всегда есть вкладка `Рабочий` (текущий worklist) и вкладка `Избранное`;
  - `Избранное` реализуется как специальная группа/список для пользователя:
    - клик по `⭐` в строке добавляет/убирает ТС в личное избранное;
    - вкладка `Избранное` фильтрует список по этой группе.

- **Карточка → действия**
  - иконка «последнее сообщение» (`📡`) остаётся, но в будущем будет дополняться ссылкой в вкладку «Сообщения», чтобы сразу прыгать к таймлайну событий.

### 3.2. Админка: Структура / Группы / Пользователи

Админ‑панель живёт **внутри того же web‑приложения**, отдельной страницей/вкладкой `Админка`. Доступна только пользователям с `is_admin` (и аналогичными правами).

#### 3.2.1. Вкладка «Структура»

- **Левая колонка** — дерево узлов:
  - корень: `Компания` (или другое имя);
  - вложенные узлы: «Управление 1», «Колонна 3», «Смена А» и т.п.;
  - для каждого узла контекстное меню:
    - «Переименовать»;
    - «Добавить подузел»;
    - «Удалить» (если нет ТС/пользователей или с подтверждением).

- **Правая часть** делится на два блока:
  - список ТС этого узла:
    - таблица: имя, госномер, UID, статус, флаги «архив», «группы»;
    - кнопки: «Создать ТС», «Перенести в другой узел», «Отправить в архив»;
  - список пользователей этого узла:
    - таблица: логин, имя, роль/флаги, старший;
    - кнопки: «Создать пользователя», «Сбросить пароль», «Отключить/включить».

- **Создание/редактирование пользователя**:
  - форма появляется в модалке или справа:
    - логин, имя;
    - выбор узла (по умолчанию текущий узел в дереве, изменить можно только при наличии прав);
    - выбор «старшего» (dropdown из пользователей в этом узле);
    - чекбоксы прав: `is_admin`, `can_manage_users`, `can_manage_units` и т.п.

#### 3.2.2. Вкладка «Группы ТС»

- Слева: список групп (`АЗС`, `Комбайны`, `VIP`, `Лизинг`, `Избранное` и т.п.).
- Справа для выбранной группы:
  - две колонки:
    - слева — «Все ТС» (с поиском по имени/UID);
    - справа — «ТС в группе».
  - кнопки `Добавить >>` / `<< Убрать` или перенаправление по клику/чекбоксу.
- Специальный случай:
  - для `Избранное` группы может быть пометка, что она «user‑scoped» (группа на пользователя), и тогда API/фронт будут привязывать выбранные ТС к конкретному `user_id`.

#### 3.2.3. Вкладка «Пользователи»

- Таблица:
  - колонки: логин, имя, узел, старший, группы, права, статус (активен/заблокирован).
  - фильтр по логину/имени.
- При клике по пользователю:
  - открывается форма с теми же полями, что в «Структуре» (узел, старший, флаги прав, группы);
  - узел выбирается через дерево (диалог выбора узла).

### 3.3. Управление объектами и архив

- **Создание ТС**
  - инициируется из вкладки «Структура» (кнопка `+ ТС` в выбранном узле) или отдельной формы;
  - поле «Подразделение»:
    - по умолчанию текущий узел;
    - редактируемо только для пользователей с правами;
  - после сохранения:
    - ТС сразу видят все пользователи этого узла и всех верхних узлов;
    - пользователи других веток НЕ видят, пока объект не перенесён или не добавлен в доступную им группу.

- **Перенос ТС**
  - в таблице ТС есть действие «Перенести»:
    - открывается диалог выбора узла в дереве;
    - после подтверждения `owner_node_id` меняется, видимость автоматически пересчитывается.

- **Архив**
  - у ТС флаг `is_deleted` (мягкое удаление):
    - обычные пользователи его не видят;
    - в админке у узла есть переключатель «Показать архивные ТС»;
  - отдельный экран/фильтр «Архив»:
    - таблица архивных ТС с датой/автором удаления и причиной;
    - кнопка «Восстановить» возвращает `is_deleted=False`.

### 3.4. Сырые данные (сообщения) — UI

Вкладка «Сообщения» в карточке юнита:

- Сверху:
  - выбор периода: «Сегодня», «24 часа», «Вчера», «7 дней», «Произвольный диапазон» (дата/время `from`/`to`);
  - чекбоксы‑фильтры:
    - «Только с координатами»;
    - «Только в движении (speed > X)»;
    - «Только с изменением топлива» (на будущее).
- Ниже — виртуализированная таблица:
  - колонки:
    - `№` — порядковый номер;
    - `Время` — локальное время по `device_ts`;
    - `Координаты` — lat/lon (или `—`, если нет);
    - `Скорость`;
    - 1–2 ключевых параметра (например, уровень топлива, зажигание);
  - при клике по строке:
    - раскрывается подстрока с полным списком `params` и, при необходимости, `raw_payload` (сырые поля).
- Подгрузка:
  - при прокрутке вниз вызывается `GET /events` с `cursor`, добавляются следующие N строк;
  - большие паузы (> N минут) визуально отмечаются разделителем: «Нет данных 1.5 ч».
- Режимы:
  - по умолчанию — «диспетчерский» (минимум колонок);
  - опционально переключатель «Расширенный» для инженеров, где показывается больше параметров/сырых полей.

### 3.5. Страница «Здоровье системы»

Отдельный экран для админов (может быть вкладкой в «Админке»):

- Карточки‑метрики:
  - «Задержка телеметрии» — максимальная/средняя разница между `now` и `latest_metrics.device_ts` по парку;
  - «Ingestion» — состояние стримера:
    - сколько юнитов в работе;
    - `events/sec` за последние N секунд;
    - длина retry‑очереди, последние ошибки (429/502).
  - «Снапшот/UnitConfig» — дата/время последнего обновления снапшота и конфигов.
- Ссылки:
  - быстрые переходы в `logs/stream_runner.log` и `logs/unit_snapshot_watch.log` (например, через скачивание последних строк).

Цель этой страницы — чтобы при жалобе «данных нет 10 минут» админ сразу видел, проблема в ingestion, в снапшоте или в UI.

### 3.6. Статусы связи и актуальность данных (план реализации)

Для Monitoring v2 хотим уйти от жёсткого одного порога `MONITORING_ONLINE_SEC` ко **внятной, но простой модели статусов**, которая учитывает и канал, и давность данных, и ожидаемую частоту сообщений.

Технически вводим три сущности:

- `expected_interval_sec` — ожидаемый интервал сообщений per unit:
  - базовое значение берём из регламента (5 минут) или UnitConfig;
  - периодически переоцениваем по реальной истории только в «живых» промежутках (когда юнит online), отбрасывая большие дырки;
  - храним рядом с юнитом (мета/кеш), пересчитываем не чаще, чем раз в 6–12 часов и только при достаточном объёме данных.
- Производные пороги:
  - `online_dynamic_sec` — «мягкий» порог offline (`k1 * expected_interval_sec` с жёстким min/max);
  - `stale_warn_sec`, `stale_crit_sec` — пороги для «онлайн, нет данных N мин» и «давно нет данных» (как производные от `expected_interval_sec`).
- `StatusResult` для Monitoring:
  - `online: bool`, `age_sec`, `reason: {"ok","no_connection","no_data","no_source"}`, `label` — текст для UI.

Алгоритм:

- считаем `age_sec` как разницу между `now` и последним `device_ts/received_ts`;
- если health всех источников красный → `reason="no_source"`, статус «нет связи с источником»;
- если `age_sec <= online_dynamic_sec` и health ок → `online=True`, `reason="ok"`;
- если `age_sec > online_dynamic_sec` и по признакам считаем, что канал реально отвалился → `online=False`, `reason="no_connection"` (тексты вида «Нет связи N мин/ч»);
- если канал жив (health ok, есть сессия), но `age_sec > stale_warn_sec` → `online=True`, `reason="no_data"` (текст «Онлайн, нет данных N мин»);
- при `age_sec > stale_crit_sec` — считаем юнит «давно мёртвым» и используем более жёсткий вариант оффлайн‑статуса.

Динамика (`expected_interval_sec`) всегда работает поверх фиксированных рамок (min/max для интервалов и порогов) и **никогда не меняется чаще, чем раз в несколько часов**, чтобы статусы были предсказуемыми для оператора. Сам UI и конкретные тексты статусов описаны в README, а мотивация и обсуждение компромиссов — в ARCHITECTURE_DIALOG.

Инструменты:

- `pipeline/cli/recalc_expected_intervals.py` — фоновой пересчёт кеша `data/expected_interval.json` (окно 2 дня, период 12 ч по умолчанию, лимит юнитов за прогон).
- `pipeline/services/expected_interval_service.py` — расчёт `expected_interval_sec` по событиям за окно, фильтрация аномальных интервалов.
- `pipeline/engine/status.py` — использует `expected_interval_sec` (из UnitConfig или кеша) для расчёта порогов и формирования строки статуса.
- При недоступности health‑файлов ingestion статус получает `reason=no_source` и текст «Нет связи с источником».
- Пересчёт интервалов логируется в `logs/expected_interval_recalc.log`; рекомендуемый фон: cron/systemd, запускающий `scripts/recalc_expected_intervals.sh` каждые 30–60 мин, с параметрами `--recalc-period-hours 12 --max-units 200 --online-threshold-sec 600`.

Пример cron (каждые 30 минут):

```
*/30 * * * * /path/to/project/scripts/recalc_expected_intervals.sh --window-days 2 --recalc-period-hours 12 --max-units 200 --online-threshold-sec 600 --min-samples 20 --alpha 0.7
```

## 8. Свежие изменения (2025-11-23)

Сделано:
- Введён unit_snapshot v2 (только локальные данные: UnitConfig + latest_metrics), legacy исключён.
- Ингест Galileosky: ASCII #L#/#D# + бинарный TLV, автозапись latest_metrics, адрес/геозоны через LocationEnricher, отдельные логи/health/prom.
- Детекция движения/зажигания per-unit (Wialon-подобно): acc/dev_status/input/ручные пороги или авто-порог по pwr_ext с гистерезисом и порогом IGNITION_VOLTAGE_DELTA; порог кэшируется в data/ignition_cache.json и переучивается по свежим событиям.
- WEB Monitoring: чипы статуса/зажигания в списке, карточка с последними сообщениями, датчиками (вкл. напряжение с двумя знаками после запятой), counters/params.

На чём остановились:
- Для части юнитов напряжение не приходит именованно (безымянные массивы) — нужно либо настроить отправку pwr_ext/pwr_int, либо дать схему маппинга индексов.
- Меню «настройки объекта» в UI пока нет; при необходимости добавить кнопку/панель редактирования UnitConfig/owner/groups.

## 9. Статусы/интервалы — состояние на 2025-11-25

- Динамические пороги на основе `expected_interval_sec` работают в `compute_status`;
- есть фоновая утилита `pipeline/cli/recalc_expected_intervals.py` + оболочка `scripts/recalc_expected_intervals.sh`, логи в `logs/expected_interval_recalc.log`;
- health‑файлы ingest (`logs/*_ingest_health.json`) учитываются: при их «красном» состоянии статус получает `reason=no_source` и текст «Нет связи с источником»;
- во фронте список/карточка используют новый `status_label`, «нет данных» (канал жив, но терминал молчит) подсвечивается отдельным цветом;
- что осталось: включить периодический запуск recalc в crontab/systemd и поднаблюдать коэффициенты `k1/k2/k3`, `WARN/CRIT_MIN_SEC` на реальных данных.

Движение/остановка/стоянка:

- ядро статуса (`status`) выдаёт:
  - `moving` — движение;
  - `stop` — короткая остановка (нет или короткий `stop_duration_s`);
  - `park_ign_on/park_ign_off` — короткая остановка с явным состоянием зажигания;
  - `stopped` — длительная стоянка (простой ≥ `STOP_TO_PARK_SEC`);
- Monitoring v2:
  - фильтр «Движение» → `moving`;
  - фильтр «Остановка» → `stop` + `park_ign_on/park_ign_off` (остановка по ПДД);
  - фильтр «Стоянка» → `stopped`;
  - чипы/иконки в карточке и статусная строка используют тот же мэппинг.
